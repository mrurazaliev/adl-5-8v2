# CODING_STYLE.md — ADL58 V2 (черновик)

## Статус анализа

Исходники предыдущих React-проектов владельца **не предоставлены**. Индивидуальный стиль программирования пока **не определён**.

Не подтверждены примерами:

- структура компонентов и naming conventions;
- паттерны `useState` / `useEffect`;
- работа с Redux Toolkit и RTK Query;
- стиль TypeScript interfaces/types;
- naming event handlers;
- подход к CRUD;
- conditional rendering;
- форматирование JSX.

Для заполнения раздела «Индивидуальный стиль» требуется минимум 2–3 репрезентативных исходных файла предыдущих проектов. До тех пор выдуманные правила стиля не добавляются.

## Индивидуальный стиль владельца

Подтверждён в текущей задаче: функциональные React-компоненты, простой код без лишних абстракций, `useState` и хуки RTK Query напрямую в компоненте, одинарные кавычки, без `any` и без новых комментариев в коде.

## Подтверждённые требования владельца

Это не выведенный стиль, а прямо заданные требования к разработке:

- простая архитектура и минимум лишних абстракций;
- функциональные React-компоненты;
- чистый TypeScript без необязательного `any`;
- Redux Toolkit для клиентского состояния;
- RTK Query для серверного состояния;
- React Hook Form + Zod + `@hookform/resolvers` для основных форм;
- Tailwind CSS v4 + shadcn/ui для интерфейса;
- никаких выдуманных API endpoints;
- никаких самовольных изменений бизнес-логики;
- серверные данные брать только из RTK Query, без мокового fallback на страницах;
- сохранять существующий Premium Fintech дизайн и переводы i18next.

## Обязательные правила для форм

- `react-hook-form` управляет полями, отправкой, ошибками валидации и состоянием submit.
- Zod описывает схему валидации; интеграция через `zodResolver`.
- Не создавать отдельный `useState` для каждого поля без необходимости.
- Не дублировать валидацию в Zod и вручную в обработчиках.
- Типы выводить из Zod-схемы (`z.infer`), для полей использовать `Controller` при работе с контролами shadcn/ui.
- Не придумывать поля, отсутствующие в требованиях или API.
- Для shadcn/ui использовать актуальный поддерживаемый способ интеграции из документации (в текущей версии — компонент `Field` вместо устаревшего `form`).

## Границы бизнес-логики

Без отдельного разрешения не реализовывать и не изменять:

- расчёт баланса долгов;
- логику переплат;
- финансовые вычисления;
- правила создания и погашения долгов;
- логику платежей;
- правила изменения финансовых записей;
- другие критические финансовые правила.

Разрешено подготавливать интерфейсы, вёрстку, визуальные элементы, формы без бизнес-обработчиков, Redux UI slices, RTK Query архитектуру, вспомогательные компоненты и тесты уже согласованной логики.

Если задача требует бизнес-решения, остановиться и запросить решение у владельца/наставника.
